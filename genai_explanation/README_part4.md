
# Part 4: GenAI Incident Explanation

Explains an event that Parts 2 and 3 have processed. It is **advisory only**: it never
executes actions, changes severity, or confirms that an attack occurred.

## Works without an API key

By default, Sentinel uses a template-based fallback. A real LLM is optional.
Only a real LLM response has `source: "llm"` and `llm_used: true`.

## Installation (Windows PowerShell, from the repository root)

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r genai_explanation\requirements.txt
```

If PowerShell blocks activation, run:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.venv\Scripts\Activate.ps1
```

## Configure an LLM (optional)

Copy the example configuration:

```powershell
copy genai_explanation\.env.example genai_explanation\.env
```

Edit `genai_explanation\.env` and set the required values. Never commit `.env`.
Set `SENTINEL_LLM_PROVIDER=openai_compatible` to use a compatible API.
Without a configured provider, the fallback should be used.

## Run the demo

```powershell
python -m genai_explanation.explain
```

## Use it from other code

```python
from pipeline.orchestrator import process_event
from genai_explanation.explain import explain_incident

processed = process_event(raw_event, detector, tracker)
explanation = explain_incident(processed)
```

Run from the repository root. The `detector` and `tracker` arguments depend on how
Parts 2 and 3 are initialized in your project.

## Input

A processed event containing `metrics` (a dictionary of numbers). Optional fields include
`event_id`, `system_id`, `timestamp`, `severity`, `is_anomaly`, `anomaly_score`,
`deviated_metrics` or `flagged_metrics`, `metric_scores`, `correlation_detected`,
and `memory_trend_detected`.

Ground-truth labels and unrelated fields are ignored and must not be sent to an LLM.

## Output

| Key | Meaning |
|---|---|
| `event_id`, `system_id`, `timestamp` | Copied from input where available |
| `status` | `ok`, `fallback`, or `error` |
| `source` | `llm`, `fallback`/`rule_based_fallback`, or `none` |
| `llm_used` | `true` only when real LLM text is used |
| `provider` | Provider name, if available |
| `incident_type` | An allowed type, or `unknown` on error |
| `severity` | Severity copied from input, or `UNKNOWN` |
| `summary` | Short, cautious explanation |
| `evidence` | Evidence generated by code from input data |
| `recommended_actions` | Advice for people; never executed automatically |
| `warnings` | Notes explaining fallback or other limitations |
| `error` | `null`, or an error message |
| `advisory_only` | Always `true` |

Part 5 and Part 6 should check `status` and `source` before using the explanation.

Allowed incident types include `possible_brute_force_activity`,
`unusual_resource_and_network_activity`, `possible_memory_leak`,
`unusual_network_activity`, `unusual_resource_usage`,
`possible_service_degradation`, `no_clear_anomaly`, and `unknown_anomaly`.


## Safety

- Evidence is built by code, not by the LLM.
- LLM output is validated for JSON, allowed incident types, length, and overconfident language.
- Event text is cleaned and treated as untrusted input.
- Only explicitly permitted fields should be sent to an LLM.

## Troubleshooting

- If `status` is `fallback`, inspect the warnings and configuration.
- HTTP 401/403: check the API key and permissions.
- HTTP 404: check the base URL and model name.
- Timeout: check the network or configured timeout.
- `ModuleNotFoundError`: run commands from the repository root.

## Limitations

Fallback explanations can only describe patterns covered by the implemented rules.
LLM safety checks are useful filters, not guarantees. Real-provider behavior should be
tested before relying on it.
